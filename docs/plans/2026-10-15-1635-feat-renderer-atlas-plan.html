Where I would start

One practical. One distinctive. One ambitious.

01 / Best first build

Tidal Reservoir

A direct relationship between height and time. Its waterline should remain readable at small terminal sizes, and its core geometry is simple.

02 / Best terminal character

Contour Descent

Contour bands make quantization part of the aesthetic. A memorable graphic identity without relying on bloom or fine particles.

03 / Most cinematic

Event Horizon

The strongest sense of an event unfolding. First verify that a coarse accretion disk still reads as a black hole before committing to its finish.

These browser previews run real fragment shaders. Pace currently draws indexed-color characters through ratatui; it has no GPU shader surface. The viable terminal path is to recreate the fields on the CPU and sample them into characters or block cells. Smooth bloom and subcell detail will change. “Cell study” shows a coarse, palette-reduced visual approximation; it does not emulate a terminal or prove speed.

Product Contract

Summary

A standalone local presentation compares ten new visual directions with live shader studies, a shared progress scrubber, and individual terminal-translation notes.

Problem Frame

Pace already has eleven visual renderers plus shuffle. New candidates should introduce different visual metaphors and meaningful countdown behavior, rather than only changing the palette of an existing effect.

Requirements

R1–R5 describe the retained presentation. R6–R11 govern production implementation.

  • R1. Present ten additional, named renderer candidates with distinct visual identities and explicit relationships between progress and appearance.
  • R2. Let the owner inspect the same start, midpoint, and completed state across all candidates using a shared scrubber.
  • R3. Keep remaining time legible over each effect and offer paused motion, including a paused initial state when reduced motion is preferred.
  • R4. Explain the visual compromise and estimated terminal fit for every candidate.
  • R5. Keep the presentation in one local HTML file that requires no server or downloaded assets.
  • R6. Aurora Veil presents moving mint and violet light curtains whose active width equals the fraction of time remaining.
  • R7. Tidal Reservoir presents blue water whose mean level equals time remaining, with restrained surface ripples and underwater caustics.
  • R8. Interference Field presents blue and pink waves from two sources, with active width equal to time remaining.
  • R9. Each renderer is selectable by its short name in all existing CLI forms and appears in help, preview, and shuffle.
  • R10. Animation is deterministic from active elapsed time; pausing and skipped frames preserve phase, and completion clears each selected field.
  • R11. Each selected renderer retains the centered numeric countdown, including the existing small-viewport fallback, and clips to its assigned viewport.

Candidate behavior

Options 01–10 above are the authoritative candidate descriptions; each expandable note states the progress mapping and the start, halfway, and zero states. Options 01 (aurora), 04 (tide), and 09 (interference) are selected for production; their descriptions and R6–R11 govern implementation. The other seven remain unselected.

Key Decisions

  • Implement Aurora Veil, Tidal Reservoir, and Interference Field. Governs R6, R7, R8, R9, R10, R11. (session-settled: user-directed — chosen over the other seven candidates: the owner selected these three after reviewing the atlas.)
  • Use the Rust port as the feasibility baseline because it is the current native terminal implementation in this workspace. This is an agent assumption.
  • Use browser GLSL to communicate the proposed appearance; compare against coarse samples without claiming identical terminal output.
  • Recommend Tidal Reservoir first for legibility and simple geometry; recommend Contour Descent for terminal identity and Event Horizon for visual ambition. These are design judgments.

Scope Boundaries

Production integration and registration of the selected three concepts are in scope. Other candidates, TypeScript changes, GPU shader support, new configuration, new dependencies, adaptive-color changes from the separate open PR, and unrelated renderer refactoring are not included. Half-block/background rendering was considered and excluded because full foreground blocks fit the existing timer and preview output paths.

Acceptance Examples

  • AE1. At 0%, Tidal Reservoir is full; at 50%, its mean waterline is halfway down; at 100%, it is empty and the clock reads 00:00.
  • AE2. At 100%, Mycelium Bloom retains a completed network while Event Horizon has lost its luminous disk; all decorative motion stops at zero.
  • AE3. After Pause, effects stay still while the scrubber can still compare progress states; Resume continues from the frozen animation phase.
  • AE4. With JavaScript disabled or WebGL unavailable, candidate prose and translation notes remain readable.

Selected-renderer acceptance

  • AE5. For aurora and interference, 0%, 50%, and 100% elapsed respectively show a full-width active field, a left half-width field, and no field.
  • AE6. Tide is full at start, has its mean surface halfway down at midpoint, and has no water at completion.
  • AE7. Repeating an elapsed-time input produces the identical field even after drawing other times or resizing; advancing by less than 100ms can change the field.
  • AE8. Each selected name works directly and through preview/shuffle; 12x1 and 12x4 viewports retain a readable remaining time.

The original AE1–AE4 describe the presentation; AE5–AE8 define production checks. Constants and final palette tuning are deferred to execution against terminal-resolution samples.

Implementation plan

Planning Contract

Key Technical Decisions

  • KTD1. Recreate each selected field on the CPU in src/effects.rs, using foreground-colored full block cells and indexed colors; add no GPU or browser runtime. Use a small shared sampling/quantization helper only when it has current callers.
  • KTD2. Register aurora, tide, and interference through model::RENDERER_NAMES, renderers::PREVIEW_RENDERERS, Effects::draw, and the existing numeric overlay. Keep original names and shuffle timing intact.
  • KTD3. Sample at cell centers with terminal-character aspect correction. Match the atlas palette and behavior at terminal resolution rather than promising browser-equivalent bloom.
  • KTD4. Use only TimerDetails active elapsed time and clamped progress; draw an empty field at completion, including zero duration and overrun input. The numeric clock remains visible.

Assumptions

The Rust port is the target. Short names are aurora, tide, and interference. The terminal supports the existing indexed-color output; capability adaptation is separate work. Each renderer is an independent delivery phase, stacked in the owner’s selection order to keep the shared registries and tests consistent.

High-Level Technical Design

The existing path remains CLI selection → Renderers composition → Effects field sampling → indexed character buffer. The clock is composed over the field.

Implementation Units

Three delivery phases. Each phase is verified, committed, pushed, and opened as its own PR before the next branch starts. Later branches include earlier phases.

Verification Contract

  • Run cargo test --all-targets, cargo fmt --check, cargo clippy --all-targets -- -D warnings, and cargo build --release on each phase.
  • Run python3 tests/terminal_smoke.py against the built release executable after each phase; confirm every registered renderer completes and restores terminal modes.
  • Use cargo test --release --test renderers measure_frame_preparation -- --ignored --nocapture to measure the existing warmed 120x40 workload. Each new field’s average frame preparation must fit below the existing 16.7ms target; this excludes terminal writes and is not a visible-FPS claim.
  • Use deterministic buffer tests for selected progress endpoints, pause/skip invariance, sub-100ms motion, completion/zero-duration/overrun, clipping, and numeric overlay. Render terminal-resolution samples for visual inspection where available.
  • No browser app or server is changed. Browser-test dispatch should report not applicable for the terminal-only implementation; do not start a dev server.

Definition of Done

Each selected renderer is usable through all existing CLI forms, help, preview, and shuffle, has its intended progress metaphor and readable clock, and passes the phase verification and independent code review. Include the presentation and enriched plan on the first PR. Keep the three PRs in phase order, preserve unrelated work, remove abandoned experimental code, record any residual findings and CI outcome, and leave the last branch available for local manual testing. No merge is authorized.
